19. COMPOUND SIGNAL SCORING
-------------------------------------------------------------------------------
A company hit by multiple independent signals in a short window (a tender
award, a news mention, a Hiring now posting, a repost) is a stronger hiring-wave
indicator than any single signal alone. Right now each lead is scored
independently with no awareness of a company's other concurrent signals.

Definition of "independent signal" for a company, within a rolling 60-day
window:
1. A tender-award lead (from TED)
2. A news-sourced won-work lead
3. An open Hiring now posting
4. A posting re-advertised (already tracked by item 17's priority-raise logic)

Scoring change:
- When a company has 2+ of these signal types active within the window, boost
  the fit/pressure score of ALL of that company's leads/postings — don't just
  boost one and leave the others unchanged.
- The boost amount and its reasoning must be visible and explained on the lead/
  posting itself (e.g. "boosted: also has an active Hiring now posting" or
  "boosted: tender award + news mention, 12 days apart") — same transparency
  standard as "why this score" elsewhere. Never a silent number change.
- This does NOT invent a new score from nothing — it's a multiplier/boost on
  top of the existing fit/pressure calculation, using only signals already
  captured in the database. No model call needed — pure logic over data
  already stored.
- A company with only one signal type is entirely unaffected — no penalty for
  having just one signal, only a boost for having more than one.

Report: how many current companies have 2+ concurrent signal types, and what
their boosted vs. unboosted scores look like — a real before/after sample, not
just a count.

Commit after each step, two lines per step. Full release gate before every
commit, screen checks as a signed-in user, both widths. Report the sample
before/after and confirm the boost reasoning is visible on screen, not hidden
in the calculation.

Decision on item 19 (owner, 2026-09-15): signal types 3 and 4 are ONE type. A
re-advertised posting is a stronger version of "has an open posting", not
independent corroboration from a separate source. A company reaches the 2+
threshold only by combining a posting with something genuinely separate — a
tender award or a news mention — never by reposting the same job. Three types
in all: tender award, news mention, open posting (re-adverts included).

HARD RULE FOR THE REST OF THIS PROJECT (2026-09-24, learned by breaking
production): CODE FIRST, DEPLOY, THEN MIGRATE — for anything that renames or
drops a column. 0047 renamed companies.rfbt_history to sector_note in one
statement while six live sites still named the old one, and applying it took
/api/jobs/companies and /api/jobs/resolve-domains down immediately. A rename is
a DROP PLUS AN ADD and no running code survives it. Every remaining step-2, 3
and 4 migration that removes or renames a column must therefore be split:

  1. add the new column (or table) — safe to migrate first, hasColumn guards it
  2. backfill it, and verify the copy independently of the script that made it
  3. deploy the code reading the NEW name, with the old column still present
  4. ONLY THEN drop the old column, in its own later migration

Before any of those, grep for every reference. Three failure shapes, hardest to
notice last: .update({col}) always fails; .select('a, col, c') fails the whole
query; .select('*') plus a property access FAILS SILENTLY — api/lead did not
crash, it just quietly stopped putting the company's sector line into outreach
drafts. Watching for exceptions does not answer "did anything break".

The remaining step-2 write surface, counted 2026-09-24: leads.status /
confirmed_by / confirmed_at / job_description / jd_version are written at 5
sites (api/lead x3, api/leads/send-pack, api/outreach); the companies columns at
api/company/employer-type and api/hiring. Only 4 selects name any of them
explicitly — everything else uses select('*') or companies(*), which is exactly
the silent-failure shape above.

26. SHARED OUTREACH CONTEXT CACHING
-------------------------------------------------------------------------------
STATUS: idea recorded, not investigated, deliberately deferred. Nothing below is measured.

Owner's idea (2026-09-25): outreach message generation currently produces one message per (workspace, lead) pair from scratch. The message genuinely has two halves — facts about the LEAD ITSELF ("Congratulations on winning the Puerto Real coating contract…"), and THIS WORKSPACE'S OFFER ("we have 5 CSWIP-certified welders available now"). The first half is a shared fact, identical for every workspace reaching out about the same lead. The second half is private business information — this workspace's actual candidate bench — and must never be shared or cached across workspaces.

PROPOSED DESIGN: split generation into a cacheable SHARED half (lead context, generated once per lead, reused by any workspace) and a PRIVATE half (this workspace's offer, generated fresh every time, never cached and never reused). It is the same shared/private split as everything else in item 20, applied to a COST OPTIMISATION rather than to a data-access boundary — which is the one thing to keep hold of when picking it up: a mistake here leaks private data while looking like a caching bug.

RULED OUT OF SCOPE, PERMANENTLY: screening questions. Unlike outreach, they are generated from ONE SPECIFIC CANDIDATE'S CV GAPS and are inherently private — reusing another workspace's screening questions would expose derived information about a private candidate. Do not investigate or build this under any framing, including "cache only the generic ones" or "cache the standard seven": the standard seven are already written in code and cost nothing to begin with (item 5), so the only thing left to cache there is the part that must never be cached.

WHY DEFERRED: this produces real savings only once a genuine second workspace exists to share the cache with. With RFBT the only real workspace today there is nobody to share with, so building it now adds complexity for zero payoff. Revisit after item 20's remaining steps (3d-4, company classification) are closed AND a real second workspace exists.

WHEN PICKED UP, INVESTIGATE BEFORE BUILDING: how outreach generation currently splits (or does not) lead-context from workspace-offer; measure the real saving from caching only the shared half; and confirm the split reintroduces no cross-workspace leak.

WHERE IT LIVES TODAY — read from the code on 2026-09-25 while recording this item, so the investigation does not start from nothing. It is a starting point, NOT a finding, and every line of it must be re-checked when the item is picked up rather than trusted:
